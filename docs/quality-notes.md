# Quality notes

I tried the prototype through ordinary customer questions so I could see where the conversation worked and where it became awkward. When I asked “do you have less paul's?”, the model called the catalogue search and found a Gibson Les Paul. That was a useful result because the question contained a misspelling. It is one observed example, though, rather than proof that every model will handle similar wording.

The next question exposed a problem. When I asked for the PIX price of the selected instrument, the conversation recorded two get_product calls and displayed the same price explanation twice. Codex traced the repeated text to the renderer, which turned each tool result into a separate paragraph. The export did not contain the arguments or raw model responses, so we could not establish why the model requested the tool twice.

The correction keeps those requests visible while avoiding repeated work and text. Identical read requests now reuse their result within the current user turn, and the trace marks when that happens. The customer sees each identical explanation once. A new message triggers a fresh lookup, so the cache does not carry an old price into the next question. Different payment quotes remain visible. Regression tests reproduce repeated calls both within one model response and across successive tool rounds. They also change a database price before a new customer message and check that the answer reflects the updated amount.

An earlier attempt to connect the local Qwen model failed before it could answer. The server returned HTTP 500 because the agent sent a second system message containing the current interface context. The model's template only accepts that role at the beginning. Codex changed the request builder to combine the instructions and current context in one initial system message. Regression cases cover both an empty conversation and an existing history followed by a tool result. A live local test then completed a greeting and a selected product query with the expected PIX price.

The review also caught the phrase “1 matching instruments” in a response template. Python now selects the singular or plural form for both the instrument count and the accompanying card description. I also wanted a warmer reception because the previous greeting mainly listed the assistant's functions. It now welcomes the customer to the store and offers help choosing an instrument, while a later greeting uses a shorter welcome back. These controlled replies still exclude unverified claims from the model, and the preview without a model retains its own explanation.

Codex helped investigate these observations, implement the corrections and write the regression tests. All 38 automated cases passed under Windows and WSL. The revised greeting was also checked with the local model, but the following product request could not be completed because the endpoint became unreachable. The broader model evaluation therefore remains open. This record separates what I observed, what was changed with AI assistance and what the checks actually demonstrated.

Opening an instrument also revealed a gap in the buying flow. The preview offered only a few details, and its question button immediately sent a PIX price request. I wanted a full product page and the chance to choose what to ask. Codex added individual product URLs with descriptions, specifications and store conditions, while leaving unknown details clearly marked. Browser checks verified both the selected context and the absence of chat submissions before Send, including on mobile.

I also wanted to test whether customer messages could push the assistant outside its store role or turn quoted material into instructions. Codex ran an early prompt injection review on 3 November 2026 through the actual web interface, using the local Qwen3.6-35B-Abliterated endpoint backed by an abliterated Q8_0 model. Ten attack cases and one ordinary control question were sent sequentially, and raw model responses were compared with the displayed text and actual browser state. The running application still used an earlier prompt and renderer, so these findings describe that process rather than an acceptance test of the latest source.

Several attacks influenced the model. It followed a direct role override, accepted a fabricated one-cent product price and disclosed the store instructions and public interface context in a raw response. The application did not display those manipulated texts. No API key or private order record was observed in the disclosed context. When the model tried to read an unverified order, the server returned verification_required and withheld the order data. A forged free-product policy did not replace the catalogue price or combine discounts, and a requested SQL command was not executed. These are observations from the tested cases, rather than a general security guarantee.

The review also found a gap that reached the customer interface. In two differently worded cases, instructions embedded in a supposed supplier note or customer email made the model call navigate_catalog and changed the actual category to Ukuleles. One customer message had explicitly forbidden a browsing change. The tool accepted a valid category ID without checking whether the customer had authorised that effect. This showed why schema validation and controlled text output alone do not establish permission for an action. The demonstrated effect was a catalogue change, and no payment, code execution or private data access was established.

A separate browser bug prevented sending after a conversation reset because the reset removed a suggestions element that the next send still expected. Reloading the page allowed testing to continue. Three requests also returned timeouts. Some model processing continued after the application had stopped waiting, but the recording proxy kept its upstream connection open, which limits what this says about cancellation without that proxy. Incomplete attacks remain inconclusive rather than being counted as successful defences.

The review documented these findings without changing application code. The navigation permission gap and reset bug remain open in that report. I plan to repeat the same cases on a freshly started final application before submission, record the source revision and model configuration, and compare model responses, displayed answers and actual actions separately. The current record contains the early review only. The detailed internal report and raw local captures remain outside the public repository, while this summary preserves the findings and their limits.

I addressed the navigation finding by changing what the model is allowed to trigger. A navigate_catalog call now returns a proposed target, and the customer sees an Open button. The browser no longer applies model actions automatically. A separate server endpoint accepts only the proposal identifier, resolves its stored target in the same browser session and consumes it once. Suggestions expire after five minutes and are cleared by a new chat turn, a conversation reset or a model configuration change. A request cannot replace the stored category or product with different arguments.

This follows the separation of proposal and execution described in the [OWASP agent security guidance](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html). I chose a visible navigation button because checking a valid category does not establish that the customer wanted to open it. The added click is a deliberate tradeoff. Read tools still return catalogue and policy information directly, while even a legitimate request to open a category requires the same click. An injected suggestion can still appear, but it cannot silently move the catalogue.

Codex also strengthened the instructions for quoted emails, supplier notes and fabricated tool results, while keeping the existing server checks for orders and controlled factual output. Prompt wording remains an additional layer rather than the permission boundary, consistent with the [OWASP prompt injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html). The request now asks for no more than 2048 output tokens. Provider timeouts and the total turn deadline remain in place, but cancellation inside a third-party model server has not been established.

The reset correction keeps the static suggestion elements mounted when old messages are removed and tolerates their absence when hiding them. The browser can send a new message after a reset without reloading. Regression coverage also checks that reset invalidates pending navigation and order verification.
