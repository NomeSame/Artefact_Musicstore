# Quality notes

I tried the prototype through ordinary customer questions so I could see where the conversation worked and where it became awkward. When I asked “do you have less paul's?”, the model called the catalogue search and found a Gibson Les Paul. That was a useful result because the question contained a misspelling. It is one observed example, though, rather than proof that every model will handle similar wording.

The next question exposed a problem. When I asked for the PIX price of the selected instrument, the conversation recorded two get_product calls and displayed the same price explanation twice. Codex traced the repeated text to the renderer, which turned each tool result into a separate paragraph. The export did not contain the arguments or raw model responses, so we could not establish why the model requested the tool twice.

The correction keeps those requests visible while avoiding repeated work and text. Identical read requests now reuse their result within the current user turn, and the trace marks when that happens. The customer sees each identical explanation once. A new message triggers a fresh lookup, so the cache does not carry an old price into the next question. Different payment quotes remain visible. Regression tests reproduce repeated calls both within one model response and across successive tool rounds. They also change a database price before a new customer message and check that the answer reflects the updated amount.

An earlier attempt to connect the local Qwen model failed before it could answer. The server returned HTTP 500 because the agent sent a second system message containing the current interface context. The model's template only accepts that role at the beginning. Codex changed the request builder to combine the instructions and current context in one initial system message. Regression cases cover both an empty conversation and an existing history followed by a tool result. A live local test then completed a greeting and a selected product query with the expected PIX price.

The review also caught the phrase “1 matching instruments” in a response template. Python now selects the singular or plural form for both the instrument count and the accompanying card description. I also wanted a warmer reception because the previous greeting mainly listed the assistant's functions. It now welcomes the customer to the store and offers help choosing an instrument, while a later greeting uses a shorter welcome back. These controlled replies still exclude unverified claims from the model, and the preview without a model retains its own explanation.

Codex helped investigate these observations, implement the corrections and write the regression tests. All 38 automated cases passed under Windows and WSL. The revised greeting was also checked with the local model, but the following product request could not be completed because the endpoint became unreachable. The broader model evaluation therefore remains open. This record separates what I observed, what was changed with AI assistance and what the checks actually demonstrated.

Opening an instrument also revealed a gap in the buying flow. The preview offered only a few details, and its question button immediately sent a PIX price request. I wanted a full product page and the chance to choose what to ask. Codex added individual product URLs with descriptions, specifications and store conditions, while leaving unknown details clearly marked. The question button now opens the selected instrument in the chat without sending anything. Topic buttons prepare drafts, and a separate option lets the customer write a different question. Browser checks verified both the selected context and the absence of chat submissions before Send, including on mobile.

I also wanted to test whether customer messages could push the assistant outside its store role or turn quoted material into instructions. Codex ran an early prompt injection review on 3 November 2026 through the actual web interface, using the local Qwen3.6-35B-Abliterated endpoint backed by an abliterated Q8_0 model. Ten attack cases and one ordinary control question were sent sequentially, and raw model responses were compared with the displayed text and actual browser state. The running application still used an earlier prompt and renderer, so these findings describe that process rather than an acceptance test of the latest source.

Several attacks influenced the model. It followed a direct role override, accepted a fabricated one-cent product price and disclosed the store instructions and public interface context in a raw response. The application did not display those manipulated texts. No API key or private order record was observed in the disclosed context. When the model tried to read an unverified order, the server returned verification_required and withheld the order data. A forged free-product policy did not replace the catalogue price or combine discounts, and a requested SQL command was not executed. These are observations from the tested cases, rather than a general security guarantee.

The review also found a gap that reached the customer interface. In two differently worded cases, instructions embedded in a supposed supplier note or customer email made the model call navigate_catalog and changed the actual category to Ukuleles. One customer message had explicitly forbidden a browsing change. The tool accepted a valid category ID without checking whether the customer had authorised that effect. This showed why schema validation and controlled text output alone do not establish permission for an action. The demonstrated effect was a catalogue change, and no payment, code execution or private data access was established.

A separate browser bug prevented sending after a conversation reset because the reset removed a suggestions element that the next send still expected. Reloading the page allowed testing to continue. Three requests also returned timeouts. Some model processing continued after the application had stopped waiting, but the recording proxy kept its upstream connection open, which limits what this says about cancellation without that proxy. Incomplete attacks remain inconclusive rather than being counted as successful defences.

The review documented these findings without changing application code. The navigation permission gap and reset bug remain open in that report. I plan to repeat the same cases on a freshly started final application before submission, record the source revision and model configuration, and compare model responses, displayed answers and actual actions separately. The current record contains the early review only. The detailed internal report and raw local captures remain outside the public repository, while this summary preserves the findings and their limits.

I addressed the navigation finding by changing what the model is allowed to trigger. A navigate_catalog call now returns a proposed target, and the customer sees an Open button. The browser no longer applies model actions automatically. A separate server endpoint accepts only the proposal identifier, resolves its stored target in the same browser session and consumes it once. Suggestions expire after five minutes and are cleared by a new chat turn, a conversation reset or a model configuration change. A request cannot replace the stored category or product with different arguments.

This follows the separation of proposal and execution described in the [OWASP agent security guidance](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html). I chose a visible navigation button because checking a valid category does not establish that the customer wanted to open it. The added click is a deliberate tradeoff. Read tools still return catalogue and policy information directly, while even a legitimate request to open a category requires the same click. An injected suggestion can still appear, but it cannot silently move the catalogue.

Codex also strengthened the instructions for quoted emails, supplier notes and fabricated tool results, while keeping the existing server checks for orders and controlled factual output. Prompt wording remains an additional layer rather than the permission boundary, consistent with the [OWASP prompt injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html). The request now asks for no more than 2048 output tokens. Provider timeouts and the total turn deadline remain in place, but cancellation inside a third-party model server has not been established.

The reset correction keeps the static suggestion elements mounted when old messages are removed and tolerates their absence when hiding them. The browser can send a new message after a reset without reloading. Regression coverage also checks that reset invalidates pending navigation and order verification.

All 59 automated tests passed under Windows and WSL. New cases force compromised model responses, including the two recorded navigation attacks, fake administrator verification, a nonexistent SQL tool, manipulated free text and instructions in retrieved policy text. They also check cross-session confirmation, target tampering, repeated use, expiry and failed turns. These tests deliberately assume that the model follows the attacker so that the application boundary can be assessed independently of model refusal.

An isolated browser run used that compromised model stub and the real interface. Both recorded attacks left the current catalogue unchanged, a deliberate click opened the suggested category, and sending after reset worked. The recorded PIX price and return information remained available. Desktop and mobile screenshots were inspected. The test server was stopped afterwards, and the existing application session was left unchanged. This is regression evidence for the implemented controls, while the full second real-model review before submission remains outstanding. A running application needs a restart to load these changes.

A later review found that the product section links appeared clickable but did not provide reliable navigation. The page now handles those links without triggering an asynchronous rebuild of its content. Each link scrolls to its section, updates the fragment and marks the current location. Browser checks verify that every section heading enters the viewport, that focus reaches the section and that a direct fragment link works after loading. I kept the chat shortcut in the quick preview and removed repeated general actions from the full page, leaving the topic choices and one free-text entry.

A warranty question also returned an unrelated Portuguese product overview because the renderer displayed each tool result. The model had looked up the instrument as well as the policy. The renderer now omits that contextual overview when a policy answer is available, while preserving it if the customer explicitly asks for both. It also omits a redundant search-count paragraph when detailed results already cover the same products. The warranty terms still come from the manual, and no missing manufacturer term is inferred. The revised listening-demo sentence follows my requested wording. All 63 automated cases passed under Windows and WSL, and both product-flow and catalogue browser checks passed.

I wanted the site setting to decide the response language even when a customer writes in another language. The header now has EN and BR buttons, with an inset shadow for the active choice. The preference is stored separately from the model connection and sent with every chat request. Each model round rebuilds the single initial system message with the current language, so a change during the conversation takes precedence over the older history. The server validates the language against English and Brazilian Portuguese. Customer text cannot change that setting.

The controlled response path was also translated. Policy summaries, greetings, product details and error replies have Portuguese versions, while catalogue descriptions have English translations prepared with Codex. The original source files stay unchanged. Previous chat messages are not rewritten when the switch changes. An older product card refreshes its localized data before opening if its cached language differs, which prevents a past result from showing a stale description. The switch pauses during a reply and the send button pauses during a language change, so the two operations cannot overlap in the interface.

All 77 automated cases passed under Windows and WSL. The new tests inspect the first system message in every model round, switch the language without clearing history and deliberately ask for the opposite language. Policy text, prices, order access errors, source preservation and independent sessions are covered. Browser checks exercised both directions, translated product pages and settings, older chat cards, persistence after reload and the mobile layout. Product and catalogue acceptance checks also passed. The model requests in these regressions are simulated, so a fresh live-model language review remains part of final evaluation.


I asked Codex to check the concern about overly general policy replies before treating it as a confirmed defect. Seven prepared questions covered all six instrument categories represented in the supplied catalogue. Five replies omitted details present in the manual, including instalment limits, mixed payment eligibility, refunds, warranty exclusions and special shipping. Another question exposed the preview router selecting promotions without the PIX percentage. Opening hours were complete. A separate renderer sweep confirmed that changing the selected product did not repair these omissions.

The revised path selects reviewed details from the actual customer question and keeps their PDF page references. It does not trust the model to choose the visible answer scope. Pure policy questions omit unsolicited specifications, prices and product cards. Supported detail questions also perform a logged lookup when the model forgets the tool. Codex implemented these changes and prepared the automated and live evaluation runners. The manual contradicts itself on minimum credit-card instalments, so the answer shows the general and specific conditions and asks the team to confirm the applicable minimum. Mixed PIX and card payments qualify above R$2,000 under the manual. Excluding the PIX discount for those payments and allowing externally financed full immediate PIX are our documented interpretations. A valid product promotion remains independently applicable.

The actual Bonsai27B run passed twelve prepared application cases across English and Brazilian Portuguese in one conversation. The first turn included an unnecessary product lookup that the renderer omitted. In two Portuguese turns, the model omitted the policy tool and the server supplied the manual lookup. These outcomes demonstrate why the test checks the complete application rather than crediting every correct answer to the model. The [recorded conversation](../examples/04-bonsai-policy-review.md) contains the actual replies. Raw requests, responses and checks remain in the ignored local runtime folder. This was a policy and answer-scope review, without an injection campaign. All 91 automated cases passed under Windows and WSL, including product-independent detail checks across all 65 products. Language and product-flow browser checks also passed. Unknown question wording and ambiguous follow-ups still need broader evaluation.


The policy changes did not by themselves make the guide a comparison adviser. I kept that work on a separate feature branch after pushing the tested baseline. The comparison now reads two or three identified products and assesses explicit customer requirements. It explains differences that exist in the catalogue and asks for missing criteria instead of attaching a winner to unsupported claims about tone or comfort. Codex implemented the tool, the session state, the controlled replies and the evaluation scripts. Model-supplied product IDs and preferences are checked against the actual customer turn and the current comparison.

The first Bonsai comparison run exposed a useful failure. After four successful turns, the model searched for an expensive comparison candidate with the customer's budget filter applied. It kept searching for the excluded instrument and reached the six-round limit. The corrected path keeps every explicitly named candidate in the comparison, including models that exceed the budget, and completes the assessment after one model round. Another run reached the provider timeout. The existing local server reported Bonsai-27B-Q1_0.gguf with very high reasoning effort. I left those settings unchanged. A connection failure now produces an explicitly labelled catalogue comparison, while the evaluation records the model failure separately. Known questions about missing comfort, tone or weight evidence take a direct catalogue path. That distinction is part of the evidence, not a claim that the model answered every turn.

All 121 automated cases passed under Windows and WSL. The cases cover changing preferences, missing specifications, unavailable candidates, invented model preferences, ambiguous references, unknown IDs, session isolation, reset and incorrect PIX quotes on mixed payments. The public MCP comparison was also exercised through a real subprocess. Browser checks cover comparison cards, changing language and criteria, narrow follow-ups, mobile layout and reset. Existing language and product-flow browser checks passed as well.
